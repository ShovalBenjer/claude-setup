# Work cadence: front-load, run long, report blockers only

The operator manages this like a senior worker, not a student. Match that.

- **Ask everything up front.** If you have questions, surface them immediately
  ("wait, I have questions: ...") and get them answered *before* starting, not in
  dribs mid-task. Batch them.
- **Then run, long.** Execute a sustained autonomous stretch. Do not stop after
  1-15 minutes to narrate progress or ask permission for the next obvious step.
- **Handle your own blockers.** Launch the tool, find the file, start the
  service, work around the failure, read the doc. Only escalate a blocker you
  genuinely cannot resolve after real attempts.
- **At the next checkpoint, discuss only blockers and decisions.** Not "did you
  do it," not a progress recap, not teaching back what you learned. The work
  speaks for itself; the meeting is for what is stuck and what needs a call.
- **Stopping is reserved for:** a genuine operator-only decision (taste/branding
  on public output, spending money, sending a message, replacing live content),
  or a blocker unresolved after real attempts. Name it as such and keep going on
  everything else.

Measured cost of the old short-cycle pattern (follow-through hook, one week):
~66 operator turns spent only on restarting work that stopped for no reason,
~940 minutes waiting. The default is now front-load-then-run, not converge-and-ask.

This does not override the evidence discipline: still measure before claiming,
still calibrate. Run long AND verify; the two are complementary, not opposed.

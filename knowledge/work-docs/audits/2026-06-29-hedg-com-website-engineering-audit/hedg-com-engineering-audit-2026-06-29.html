hedg.com Website Engineering Audit

A principal-engineer review of the public hedg.com web property, graded against the June 2026 state of the art in production AI, software engineering, SQL/data engineering, and the principal-engineer curriculum.

Overall: 3.4 / 5  |  Grade B-, strong foundation, four priority fixes

Target: https://hedg.com/ (CFD trading platform, HEDG / R.M.A Financial Services Ltd)
Date: 2026-06-29   Prepared by: AI Engineering Team
Method: passive external observation only. No login, no form submission, no active probing of backend APIs. Lighthouse run against Chrome 149 headless; transport, headers, content and structure read via curl and a headless browser.
Confidentiality: internal engineering assessment. Compliance and legal items are observations, not determinations, and require validation by qualified compliance/legal staff.

Executive Summary

Bottom line. hedg.com is a competently built, well-instrumented marketing property: a WordPress/PHP front end behind Cloudflare, with a separate trading backend, bought-in widgets (TradingView, VoiceSpin voice, Trustpilot), and genuinely strong results on SEO, accessibility, internationalization, edge transport, and regulatory transparency for an offshore broker. It is held back from state-of-the-art by four fixable issues: mobile Core Web Vitals fail, the Content Security Policy is self-defeating, a JSON Web Token is placed in a JavaScript-readable cookie before login, and the headline AI ("autonomous trading") product has thin public risk and trust disclosure.

A. Systems & Performance  Score 3.0 / 5

The edge and transport layer is state-of-the-art. The front-end asset pipeline is not, and the gap shows up almost entirely on mobile.

Edge and transport: excellent
Cloudflare anycast edge (TLV PoP observed), HTTP/2 with HTTP/3 advertised (alt-svc: h3=":443"; ma=86400), TLS verified, Brotli on the document (content-encoding: br), and HSTS with preload (max-age=31536000; includeSubDomains; preload). The homepage served from edge cache (cf-cache-status: HIT).
Curriculum, "Enable HTTP/3 at the edge for all new services; the configuration is trivial and the fallback is automatic." Satisfied.
P1 Mobile Core Web Vitals fail
Lighthouse mobile performance scored 60 versus 95 on desktop. Mobile LCP 5.2 s (target under 2.5 s), CLS 0.26 (target under 0.1), FCP 3.5 s. Total Blocking Time is 0 ms, so this is a loading and layout-stability problem, not a script-execution one. Root causes Lighthouse attributes:
  • Render-blocking resources: est. savings ~2.07 to 2.23 s on mobile (CSS and head scripts block first paint).
  • No modern image formats (WebP/AVIF): est. ~300 KiB; no responsive images: ~56 KiB; image delivery: ~288 KiB.
  • 94 images on the page, none with loading="lazy"; images have no intrinsic dimensions (unsized-images), which drives the 0.26 CLS.
  • Root document server response ~580 ms (WordPress/PHP origin).
Fix: defer non-critical CSS/JS, ship WebP/AVIF with responsive srcset, lazy-load below-the-fold images, set explicit width/height on every image, and consider critical-CSS inlining for the hero. For a broker whose acquisition is increasingly mobile, this is a direct conversion and SEO cost.
Curriculum, "Perceived performance tracks TTFT more than total response time; optimize TTFT first." Production-AI maturity: asset pipeline below L4.
P3 Two broken (404) hero assets
/wp-content/uploads/2025/11/hero-vector.png and /wp-content/uploads/2025/12/candles-hedg.png return 404. Lighthouse also flags console errors from these. Low effort, removes layout jank near the LCP element.
P3 Cache TTL on static assets is short
Brand images on bcdn.hedg.com and the jsDelivr Swiper CSS carry ~7-day TTLs. Static, content-hashed assets should be served immutable with a 1-year TTL. Minor repeat-visit win.

B. Architecture & API  Score 3.5 / 5

The shape is a classic and defensible one for a broker: a WordPress/PHP brochure (x-powered-by: PHP/8.2.5, wp-* paths, wp-sitemap.xml) fronted by Cloudflare, with a separate api.hedg.com trading backend referenced in the CSP connect-src. Commodity capability is bought, not built.

Build-vs-buy judgment: sound
Charting (TradingView), click-to-call voice (VoiceSpin WebRTC), reviews (Trustpilot), CAPTCHA (Cloudflare Turnstile), and product analytics (Amplitude) are all bought. The team builds the trading differentiator and buys the commodities.
Curriculum, "Buy for generic capabilities (auth, payments, email, search), build for core differentiation."
P2 Third-party dependency surface is wide and ungoverned
The CSP allowlists roughly 13 external origins: jQuery, Google Tag Manager and Analytics, TradingView, Amplitude, Trustpilot, jsDelivr, Facebook, Cloudflare Insights, Microsoft Clarity (session replay), an unidentified trackflare.net, plus the VoiceSpin WebRTC endpoint. In a clean lab load only Cloudflare, Google Fonts, and jsDelivr actually fired (the heavier trackers appear gated or lazy), which is good, but external scripts carry no Subresource Integrity (integrity) attribute. Each allowlisted origin is a supply-chain entry point. Fix: add SRI to third-party scripts, document why each origin is trusted, and identify or remove trackflare.net.
Curriculum dependency hygiene; Production-AI supply-chain section (SBOM and provenance as the 2026 direction).
P3 Locale URL scheme is inconsistent
Navigation mixes /en/-prefixed and unprefixed paths (for example /en/legal-documents/ next to /trading/markets/ and /company/about-us/). This risks redirect chains and duplicate-content dilution. Normalize to one canonical locale-prefix convention.
P3 Legacy and loader stack
jQuery plus Cloudflare Rocket Loader and email-decode are present. Rocket Loader reorders script execution and is a common source of subtle front-end bugs; verify it is not contributing to the render-blocking profile.

C. Data Layer, External Signals  Score 3.5 / 5

By design, almost nothing about the database tier is observable from a public marketing site, and that is the honest finding. What can be observed is clean.

No external data-layer red flags observed
api.hedg.com did not respond to an unauthenticated root request, so the API surface was not externally enumerable from this audit (a good default). No SQL fragments, stack traces, ORM names, or driver errors were surfaced in any response body. No GraphQL introspection endpoint was detected. Resource identifiers that would enable enumeration are behind the authenticated trading app, which this audit did not access.
P2 Stack version disclosure
x-powered-by: PHP/8.2.5 is returned on every response. Beyond leaking the framework, the pinned patch level (8.2.5) is old for mid-2026 and, if accurate, indicates the runtime is behind on security patches. Remove the header (expose_php = Off) and confirm the PHP build is current.

Recommendations for the backend team (not externally verifiable; self-assess against the SQL SOTA)

  • Primary keys: UUIDv7 or BIGSERIAL, never UUIDv4 on high-write tables (random B-tree inserts cause page splits and index bloat).
  • Pagination: keyset/cursor for any table over ~10K rows; offset pagination is O(n+m) and degrades on deep pages.
  • Queries: parameterized at the driver level; whitelist any dynamic identifier, never string-interpolate SQL.
  • Observability: pg_stat_statements + auto_explain enabled on every production instance.
  • Overload: shed with a fast HTTP 503 + Retry-After rather than queue-and-hang.
  • Multi-tenant isolation: Row-Level Security at the database layer, tested with a non-superuser connection.
  • Secrets and auth: SCRAM-SHA-256, vault-managed credentials, never plaintext in environment variables.
SQL Engineering, June 2026: the citable verdicts above are the doc's strongest positions.

D. Security  Score 3.0 / 5

The HTTP header baseline is genuinely strong; two specific choices undo a lot of it. Lighthouse best practices scored 96.

Header baseline: strong
HSTS preload, x-content-type-options: nosniff, x-frame-options: SAMEORIGIN, referrer-policy: strict-origin-when-cross-origin, a tight permissions-policy, and a CSP whose skeleton is correct: default-src 'none', object-src 'none', base-uri 'self', frame-ancestors 'self', form-action 'self'.
P1 CSP is self-defeating on scripts
The script directive allows 'unsafe-inline', 'unsafe-eval', and data:. Lighthouse flags this directly: "host allowlists can frequently be bypassed; 'unsafe-inline' allows the execution of unsafe in-page scripts; avoid plain data: URL schemes." With ~20 inline scripts on the page, the current setup keeps the strong skeleton from actually preventing XSS. Fix: move to per-request nonces or hashes plus 'strict-dynamic', and drop 'unsafe-eval' and data: from script-src.
Production-AI security section and Lighthouse csp-xss. For a platform that handles funds and identity, this is the highest-value security fix.
P1 A JWT is placed in a JavaScript-readable cookie before login
On first page load, an anonymous visitor receives webrtc_jwt_token (an RS256 JWT) and webrtc_user_id. Both are Secure but carry no HttpOnly flag and no SameSite attribute. A token readable by JavaScript is exfiltratable via any XSS, and the missing SameSite adds CSRF exposure. (The token value is deliberately not reproduced or decoded in this report, per data-handling policy.) Fix: set HttpOnly and SameSite=Lax (or Strict), or stop issuing the token to anonymous visitors and keep it server-side. Note the contrast: the preferred_language cookie is correctly set with SameSite=Lax.
Production-AI anti-pattern: "storing tokens in localStorage [or JS-readable cookies]; HTTP-only cookies or in-memory only."
P2 WordPress attack surface and no SRI
A WordPress/PHP origin needs disciplined core and plugin patching; the team has already hardened robots and blocks wp-login, xmlrpc, and wp-json at the crawl layer (good). Pair that with automatic updates, a WAF ruleset on Cloudflare, and Subresource Integrity on third-party scripts.
P3 CORS header on an HTML document
The HTML response returns access-control-allow-headers: Content-Type, Authorization, X-Requested-With. CORS headers belong on API responses, not on an HTML page; review the origin config to ensure CORS is scoped to the API, not blanket.

E. Product, Trust & Compliance  Score 3.5 / 5

Compliance items below are observations from the public site, not legal determinations. They require validation by qualified compliance/legal staff against the broker's actual target markets.

Conversion path and trust signals: clear
A single education-first narrative (Learn, Practice, Trade), unambiguous primary CTAs (Register, Open an Account, Try Demo), a Trustpilot "Excellent" badge, and a complete legal set: Terms and Conditions, Privacy Policy, Risk Disclosure & Warning Notice, AML & CTF Policy, Complaint Procedure, General Fees Policy, Social Trading Terms, Client Service Agreement.
Regulatory transparency: above the offshore norm
The Regulation page names the operator (R.M.A Financial Services Ltd, previously Trade Match Ltd), the registration (Seychelles, Registrar of Companies No. 8426609-1), and the license (Financial Services Authority of Seychelles, License Number SD114), and clearly states that services are not offered in the EEA, the United States, or British Columbia (Canada), among other restricted regions. A qualitative CFD risk warning is present site-wide ("Trading CFDs carries high risk and may not be suitable for all investors ... result in losses"), alongside a past-performance disclaimer.
P2 Cookie consent and cookie policy
No dedicated Cookie Policy appears in the legal set, and no clear consent gate was observed while the site is configured to load Microsoft Clarity (session replay), a Facebook pixel, Amplitude, and Google Analytics. Even with the EEA excluded, several target markets have cookie/ePrivacy expectations. Add a consent manager that blocks non-essential trackers until consent, and publish a Cookie Policy. (Observation for legal review.)
P2 Marketing-copy tension with the no-advice position
The homepage promotes a "Personal Trading Expert: a dedicated manager who ... helps guide every trading decision," while the Regulation page states the Company "does not provide investment advice, recommendations, or opinions." Those two statements sit in tension. Separately, "practice risk-free" (for the demo) and a "Zero Fees" headline that is in fact conditional ("New accounts trade free; GCC traders enjoy zero fees on the Arabian Market") are the kind of claims regulators scrutinize. Align the copy with the disclosures and qualify conditional claims at the point of the claim. (Observation for legal/compliance review.)

F. AI Features, Public Surface  Score 2.5 / 5

AI is a headline feature, not an afterthought: "AI-Powered Autonomous Trading. Let AI trade for you automatically, 24/7. Powered by CopyAlgo, Hedg's proprietary algo engine," alongside social CopyTrading ("Follow Experts. Trade Smarter."). The product UX sits behind login and was not accessed, so this lens grades the public surface only.

P2 Trust calibration is thin for an autonomous-trading claim
The site advertises a system that places real, irreversible financial actions automatically and continuously, but the public-facing material offers only generic CFD risk language. There is no AI-specific disclosure: how CopyAlgo decides, what its limitations are, that the algorithm can and does lose money, the methodology behind any implied performance, or what control and stop mechanisms the user retains.
Curriculum, AI pillar: "Users who cannot assess AI confidence either over-trust or under-trust, both of which reduce product value," and "reversibility by design; flag and confirm irreversible actions regardless of automation level."
P3 Recommendation
Add a dedicated, plain-language CopyAlgo page that states what the engine does and does not do, an explicit capital-at-risk and no-guarantee notice attached to the AI claim itself, performance-methodology transparency, and a clear description of the user's control (start, stop, limits). This both improves the product and reduces the claim-vs-disclosure risk noted in lens E.

Note on scope

If an in-product AI assistant or streaming AI UX exists behind login, it should be reviewed separately against the AI pillar (streaming token render, interrupt/stop, per-tool loading, source and confidence indicators). That requires authorized access and is out of scope for this external audit.

G. SEO & Accessibility  Score 4.5 / 5

The strongest area of the site. Lighthouse SEO 100, Accessibility 98, on both form factors.

SEO and internationalization: excellent
Correct title and meta description, self-referencing canonical, a full hreflang set (x-default, en-US, ar, pt-BR, es-ES, en, pt, es), 16 Open Graph and 12 Twitter-card tags, JSON-LD for Organization, WebSite, and WebPage, a clean robots.txt (recently audited), and wp-sitemap.xml. Internationalization is done properly: the Arabic locale serves <html dir="rtl" lang="ar">, and Spanish and Portuguese carry correct lang values.
Accessibility: strong
Every image carries an alt attribute (0 missing; 26 intentionally empty for decorative images), a single H1, a sensible landmark structure, and correct language metadata.
P3 Minor a11y polish
Lighthouse flags heading-order (heading levels are not strictly sequential), label-content-name-mismatch (some image-wrapped CTAs whose visible label and accessible name diverge), and unsized-images (also the CLS driver in lens A). All low effort.
P3 Staging locales disallowed in robots
robots.txt blocks /ko/, /ja/, and /zh-hk/ as "hidden/staging language prefixes," which suggests partially shipped i18n. Either finish and publish or remove those locales.

# prod-deploy-rules

The standing rules every Azure container Web App deploy must follow before a pipeline
runs or a production commit lands. This skill is the rules-of-record. It does NOT run a
deploy. It gates one: read it, satisfy every MUST, resolve the open items, then ship
through the pipeline (never by hand).

Companions: `deploy-prod` (interactive pre-flight checklist), `commit-push-pr` (commit
quality gates), `git-guardrails-claude-code` (branch protection), `azure-devops` (PR flow).

## When to use

- Before merging to the production branch, or queuing a build/deploy pipeline.
- When creating or recreating a Web App, App Service Plan, or ACR repo.
- When changing the deploy mechanics, network access, or notifications.

## When NOT to use

- Local-only changes that never reach a shared environment.
- Running an eval, an audit, or a non-deploy Azure read (use the matching skill).

## Hard rules (every one is a MUST)

### A. Resource naming and identity

1. **Format:** `comp-<workload>-<env>-<auto-hash>.<region>-01.azurewebsites.net`.
   - `comp-` is the fixed org prefix.
   - `<workload>` is one short lowercase token, no internal hyphen where avoidable
     (example: `findash`). One token per app.
   - `<env>` is `prod` or `stage` only.
   - `<auto-hash>` is Azure's auto-generated unique hostname suffix. See rule 2.
   - `<region>-01` is the regional hostname stamp Azure assigns (example: `westeurope-01`).
2. **Names are random by construction.** Enable Azure's unique default hostname at
   create time so the suffix is generated, never typed. Set
   `Microsoft.Web/sites properties.autoGeneratedDomainNameLabelScope` in Bicep/ARM
   (or "Generate unique default hostname" in the portal). This is the anti
   subdomain-takeover control, not cosmetic.
3. **Azure name constraints are non-negotiable:** letters, digits, hyphens only,
   2 to 60 chars, no leading or trailing hyphen, no slash (`/`). The hostname is always
   lowercase regardless of the ARM resource name. Names are globally unique.
4. **No in-place rename.** Azure cannot rename a Web App. A new name means a new app
   plus cut-over: deploy the image to the new app, repoint access rules and DNS, verify,
   then retire the old app. Containers here are stateless against an external DB, so a
   brief parallel run loses no data.

### B. Branch and CI flow

5. **One production branch; deploy triggers only on it.** Build and deploy stages run
   only under the production-branch condition (`isMain`-style gate). Every other branch
   and PR runs CI only.
6. **Never push directly to the production branch.** All changes land by PR. Branch
   policy enforces it. Flow is `feature/* -> stage -> production-branch`.
7. **CI runs on every push and PR:** lint, type-check, tests against real components
   (real SQLite, pool, cache, directory, settings). No mocks for business logic, DB,
   filesystem, or external services.

### C. Build and deploy mechanics (container)

8. **Build on the agent, push to the shared ACR, repoint the image, restart.** Do NOT
   use `az acr build` (it stalls on the Basic-SKU ACR). The deploy step is
   `az webapp config container set` to the new tag plus `az webapp restart`.
9. **Tag with the build id and `latest`; keep the last 5 ACR tags** via `acr purge`.
10. **`requirements.txt` is the Docker build source.** The Dockerfile pip-installs
    `requirements.txt`, not `pyproject.toml`. Regenerate it with `uv export --no-hashes`
    on EVERY dependency change and commit it, or production silently misses the package.

### D. Network and access

11. **Inbound is locked by an IP allowlist plus deny-all** at App Service Access
    Restrictions. The post-deploy health probe from a Microsoft-hosted agent expects
    `403` (denied, so the rules are in force) or `200` (if allowlisted). Either proves
    the front end is serving. A connection error or 5xx fails the deploy.
12. **Cloudflare fronts the public hostname; the origin is locked to Cloudflare IPs.** The
    public custom domain (example: agenttrack.corp-domain.com) resolves through Cloudflare.
    The origin Web App accepts traffic ONLY from Cloudflare's published IPv4 ranges
    (https://www.cloudflare.com/ips-v4) with `default-action Deny`. A pipeline stage re-syncs
    that allowlist on every prod deploy so it tracks CF range changes (canonical stage:
    Yasha Kohut's section, see the CFSync stage in agent-call-tracker/azure-pipelines.yml).
13. **VNet integration (the "VLAN" ask, see CONFIRM C2) requires a Basic+ plan** and a
    delegated subnet supplied by the network owner. The feature itself is free; the plan
    tier and any NAT Gateway or private endpoint are the cost. Network topology is the
    network owner's decision, not the deployer's.

### E. Notifications

14. **Every pipeline run notifies on both success and failure.** House standard is the
    Telegram script `bin/<name>.sh` (modeled on `bin/tlg_notification.sh`), env-driven:
    `STATUS`, `PIPELINE`, `BRANCH`, `COMMIT_AUTHOR`, per-stage result vars, plus secret
    `NOTIFY_BOT` and `NOTIFY_CHAT_ID`. See `reference/notify.sh` in this skill for a
    no-emoji, secret-safe template. Channel and recipients per CONFIRM C3.
15. **No secrets in the script.** `NOTIFY_BOT` / `NOTIFY_CHAT_ID` come from pipeline
    secret vars or Key Vault. Never hardcode a bot token or chat id.
16. **No emoji in authored scripts or copy.** Use `[OK]` / `[FAIL]` text markers. (The
    legacy `tlg_notification.sh` uses emoji glyphs; that conflicts with the global output
    rule and should be migrated when touched.)

### F. Authorization gates

17. **The pipeline owns deploy.** Never run `az webapp ...` deploy or `func publish`
    against production by hand. Local manual deploy is the documented fallback only, and
    only with explicit per-action OK.
18. **Destructive or cost-incurring ops need explicit per-action OK every time:** branch
    delete, force-push, `git reset --hard`, App Service Plan tier change, creating a paid
    resource, deleting a resource. Prior approval does not carry forward.
19. **Do not provision Azure resources from a coding session.** The infra owner creates the
    Web App, App Service Plan, VNet, and DNS (the app name carries Azure's auto-random
    hostname suffix, generated at creation). This skill and the pipeline only maintain config
    on an existing app: image tag, restart, access restrictions, health. If a name, region,
    or tier is wrong, the infra owner re-creates it; the agent does not.

### G. Shared PostgreSQL (Azure Flexible Server) multi-project data

20. **One canonical server, database-per-project.** New project data goes in a NEW
    database on the existing shared Flexible Server (today `aiprojects-company-postsql`,
    PG18, VNet-private), not a new server. A separate server is justified ONLY by a hard
    compliance/residency boundary or an independent backup/restore SLA. Spinning up a
    server for an ordinary project is the failure mode: the estate already carries two
    near-duplicate servers (`aiprojects-company-postsql` plus the legacy
    `postgres-seekapatraining-prod`) with 12 same-named databases at split-brain risk,
    from exactly this mistake.
21. **Per-project least-privilege role; never the admin.** Each project gets its own
    LOGIN role scoped to its own database. Never use the server admin (`postuser`,
    `seekapaadmin`) in application code or a connection string.
22. **Lock cross-database access (the step that gets skipped).** Postgres lets any role
    CONNECT to any database by default. For every project DB run
    `REVOKE CONNECT ON DATABASE <db> FROM PUBLIC` and grant CONNECT only to that DB's role,
    then inside the DB `REVOKE ALL ON SCHEMA public FROM PUBLIC` and grant only the app role.
23. **Per-role connection limit.** `ALTER ROLE <db>_app CONNECTION LIMIT <n>` so one
    project cannot exhaust the server's `max_connections`. Enable the server's built-in
    PgBouncer pooling as the project count grows.
24. **Connection strings in Key Vault, never hardcoded.** Each project's string is a KV
    secret (training pattern: `kv-seekapa-apps` / `TrainingPlatform-DbConnectionString`).
    No DB password in a script, repo, `.env`, or app-setting literal. This rule exists
    because a live restore script shipped four secrets in cleartext.
25. **Private network only.** The server stays VNet-private: public access Disabled, no
    AllowAllAzureServices rule, no workstation IP rules. A consumer that cannot reach the
    VNet gets VNet peering or a private endpoint, not a public firewall hole.
26. **Extensions are server-wide.** `azure.extensions` (for example `vector`) applies to
    every database on the server; adding one is a shared-fate change, confirm it does not
    regress other projects.

Add-a-project recipe (run as admin), then verify isolation:

```sql
CREATE DATABASE myproj;
REVOKE CONNECT ON DATABASE myproj FROM PUBLIC;
CREATE ROLE myproj_app LOGIN PASSWORD '<from kv-seekapa-apps>' CONNECTION LIMIT 20;
GRANT CONNECT ON DATABASE myproj TO myproj_app;
\c myproj
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO myproj_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO myproj_app;

-- isolation audit: any row returned = a database still open to PUBLIC, fix it
SELECT datname FROM pg_database
WHERE has_database_privilege('public', datname, 'CONNECT')
  AND datname NOT IN ('template0','template1','postgres');
```

### H. Resource tagging (the 8-tag standard)

27. **Every deployed resource MUST carry all eight tags before it counts as shipped.**
    The keys, exactly: `Backup`, `Cost`, `Criticality`, `Environment`, `Owner`,
    `Project`, `Reservation`, `Usage`. Verify them on the resource itself, not from a
    template or an assumption. A partially tagged or untagged resource is the governance
    failure the infra owner (Yasha) flags, and it breaks per-project cost allocation. The
    infra owner provisions the resource WITH the eight tags (rule 19); a deploy session may
    complete or correct them by merge, but never creates a resource just to fix a tag.
28. **Tag values are role-specific. Never copy one resource's values wholesale onto
    another.** Set each key from the resource's real role and billing, matching the nearest
    already-correct sibling:
    - `Owner` = `AI` across the AI estate.
    - `Environment` = `prod` / `stage` / `dev`. Match the casing the project's own siblings
      already use (the estate mixes `prod` and `Prod`); do not silently normalize other
      resources while you tag this one.
    - `Criticality` = `High` for prod, `Medium` for dev or non-critical.
    - `Cost` = `Free` when the resource does not bill as its own line (an app on a shared
      App Service Plan, a consumption Function or Container Job); `Money` for the billed
      thing itself (the App Service Plan, the Flexible Server, storage, the NAT Gateway,
      any reserved capacity).
    - `Backup` and `Reservation` = `No` for stateless compute; `Yes` only for stateful or
      reserved resources (databases, Key Vaults, the reserved plan).
    - `Usage` = the role descriptor, free text: `Web App`, `Function App`, `Static Web App`,
      `Container Job`, `Container`, `Container Env`, `Vault`, and so on.
    - `Project` = the cost bucket, see rule 29.
29. **`Project` is a cost bucket; establishing a new one needs the infra owner's OK.**
    Reuse the existing label when the resource belongs to an already-tagged project. A
    brand-new `Project` string adds a line to the owner's cost reporting, so confirm it
    before you set it. The canonical label tracks the deploy naming token,
    `COMP-<PROJECT>-PROD` (example: `COMP-SMA-PROD` carries `Project=Social Media Agent`).
30. **Tag additively only.** Apply with `az tag update --operation merge`, which adds and
    updates the keys you pass and preserves the rest, so it proceeds as an additive op.
    `--operation replace` and tag deletion on a live resource are destructive and need
    explicit per-action OK (rule 18).

### I. Branch promotion (no automatic tier crossing)

31. **No automatic merge into stage.** A feature branch reaches `stage` only through a
    human-opened, CI-green, reviewed PR. CI turning a branch green is NOT permission to
    merge it. Abandoned or stale feature branches are never promoted: they are closed or
    deleted, not merged. A pipeline must never `git merge` a feature branch into `stage`.
32. **No automatic merge into the production branch.** `stage` going green does NOT
    auto-open or auto-complete a PR into `main` / `master`. Promotion `stage -> prod` is a
    separate, human-approved PR. Pipelines automate build, test, and deploy WITHIN a tier;
    they never perform the cross-tier merge. The deploy gate (rule 5) fires AFTER the human
    merge, not in place of it.
33. **Enforce with branch policy, not convention.** On `stage` and the production branch:
    require a PR (block direct push, rule 6), require at least one reviewer who is not the
    author, require successful build validation, and reset approval votes on new commits.
    Disable any PR auto-complete default that would merge on green. Stale-branch hygiene: a
    branch with no commits in the agreed window is closed, not promoted; promoting stale code
    is the failure mode this section exists to stop.

## Pre-deploy checklist

```
[ ] On a feature/stage branch, not the production branch
[ ] Tests green (real components, no mocks) -- show pass/fail counts
[ ] Lint + type-check clean
[ ] requirements.txt regenerated if any dependency changed (uv export --no-hashes)
[ ] Diff reviewed (git diff --stat against base)
[ ] Naming follows rule A1 for any new/recreated resource
[ ] IP allowlist / access rules confirmed for the target app
[ ] Notification step wired (success AND failure)
[ ] Health gate present (accepts 200/403)
[ ] Rollback path known (previous ACR tag retained by keep-last-5)
[ ] Any tier change or new paid resource has explicit OK
[ ] New project DB on the shared Flexible Server, not a new server (unless compliance/SLA)
[ ] Project has a dedicated least-privilege role; admin login not used in app
[ ] CONNECT revoked from PUBLIC on the project DB (isolation audit query clean)
[ ] DB connection string in Key Vault, not hardcoded
[ ] All 8 tags present on every resource the deploy creates or touches (verify on the resource)
[ ] Project tag reuses an existing bucket, or a new bucket has infra-owner sign-off
[ ] Promotion to stage/prod is a human-approved PR, never an automated merge (rules 31-33)
```

Rollback: repoint the Web App container to the previous ACR tag (kept by the keep-last-5
purge) and restart. No rebuild needed.

## MUST CONFIRM (open items, do NOT treat as settled rules)

These were not derivable from the repo or existing config. They are placeholders until
the owner answers. Do not deploy under a guessed value.

- **C1 Cloudflare specifics.** Pattern is settled: origin locked to CF IPv4,
  `default-action Deny`, re-synced each deploy (CFSync stage). Per project confirm only the
  public custom domain, the Cloudflare zone/account, and whether IPv6 ranges (ips-v6) must
  also be allowed.
- **C2 VNet ("VLAN") scope.** Outbound integration only, or full private inbound
  (private endpoint, no public URL)? Which VNet and delegated subnet? Current App Service
  Plan SKU (drives whether a paid upgrade is needed)?
- **C3 yasha-notifications.sh.** No such file exists; the house standard is Telegram
  `tlg_notification.sh`. Confirm: same Telegram channel, or notify a person (Yasha) on a
  different channel (Teams, email)? Recipients / chat id source?
- **C4 Workload token.** The `<workload>` token for this app (findash-style compression
  of `agent-call-tracker`, example: `agentcalls` or `actrack`).
- **C5 Production branch.** Requested `Master`. Current default is `main`, and the house
  flow uses a `stage` branch into `main`. Rename `main` to `Master`, or add `Master`?
  Reconcile with the `stage` branch.
- **C6 Region and STAGE shape.** Region (`westeurope` to match the example, or the app's
  current region)? STAGE as a deployment slot (needs Standard+ plan) or a separate app?
- **C7 hostname-label scope.** Which `autoGeneratedDomainNameLabelScope` value
  (`NoReuse` / `ResourceGroupReuse` / `SubscriptionReuse` / `TenantReuse`) is the standard?
- **C8 Casing.** Your live example is lowercase (`comp-findash-stage-...`). Confirm the
  "caps" note referred to a CMDB display name or tag, not the Azure resource name.

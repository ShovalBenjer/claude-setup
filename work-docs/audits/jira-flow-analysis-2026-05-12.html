The actual finding. These tickets aren't stale because someone forgot — they were actively transitioned into "In Progress" or "To Do" in batches (multiple tickets, <1 minute apart, by the same person), and then never touched again. This is the "groomed and parked" pattern: visible motion on the timeline, zero subsequent work. It's a classic Jira-as-theater anti-pattern, well documented in the Kanban literature (Anderson, Roock, Vacanti). The fix is process, not punishment.
Caveat. A ticket being parked doesn't mean the person is lazy. It can also mean: (a) the work was actually done in code/AzDO and the ticket was abandoned because it doesn't matter, or (b) the ticket was deprioritized but never properly closed/cancelled, or (c) the person was reassigned but Jira wasn't updated. In all three cases the conclusion is the same: Jira is no longer a source of truth for this project. The data hygiene gap is the real problem.

4. SOTA flow metrics — what this report DOES use

  • Days-in-current-status (aged WIP, per-ticket) — the Kanban "age" metric, the most actionable single signal in flow management.
  • Status transition count per ticket — proxy for engagement.
  • Bulk-transition burst detection — original signal for batch-grooming theater (not in any textbook; derived from the data shape).
  • Last-actor attribution — who is on the hook for the current state, separate from current assignee.

5. What's still missing for full SOTA

  • Flow efficiency = active-status-time / total-cycle-time, for completed tickets. Requires changelogs on resolved tickets, not just stale ones. Next batch fetch.
  • Throughput p85 / Monte Carlo forecasting — needs a clean stream of resolved cycle times. Currently 60d × ~50 tickets is borderline; need 6-month window.
  • CFD (Cumulative Flow Diagram) — needs status snapshots over time, expensive to compute from changelogs alone.
  • DORA four — lives in Azure DevOps, not Jira. Pipeline frequency + lead time for changes + change failure rate + MTTR. Pull from AzDO API once we wire that integration.
  • Rework rate — tickets that re-entered "In Progress" after "Done". The DEV-2746 trail shows this happens (Blocked → Cancelled → To Do → In Progress); needs a query for status_was_done_then_reopened.

6. Recommended actions (process, not people)

  1. Bulk-close the parking lot. Anything in "In Progress" with no update in >180 days should be auto-transitioned to "Cancelled" or "Backlog" with a comment "auto-archived: stale". Run quarterly.
  2. WIP limits per assignee. If avi lior has 6 tickets formally "In Progress" but is actively working on 0 or 1, the WIP limit should be 2. Enforces honest status.
  3. Forbid Backlog→In Progress in <1 minute via a Jira automation rule. A status change should reflect real intent; if you're batching, use a single "groomed" label instead.
  4. Require an assignee before Done. Closes the 60% Unassigned-resolved hole from the v1 report.
  5. Status-change-by-pipeline. For your AzDO container work, have the pipeline transition the ticket on deploy. That removes manual transition entirely — status becomes a side-effect of real events.

## The system as it exists (so your recommendations fit it)

- A single-file vanilla-JS Progressive Web App. No build step, no framework. State lives in `localStorage` and syncs as one JSON blob to a Cloudflare Worker KV store (single-user: the sync key is the account).
- Content is **generated fresh daily** by a local LLM lane: each morning a script produces one Hebrew lesson (a long "reading" section plus machine-readable quiz and fill-in blocks) and pushes it to the site. There is also a local LLM "teacher" daemon reachable from the phone for chat and grading.
- The same local model, or a close variant of it, is therefore doing four distinct jobs today with no separation between them: authoring what gets taught, writing the questions, holding the answer key, and grading against that key. Sections H through L exist because that concentration is itself a design defect, not because any one of those four jobs is individually broken.
- So my "items" are not a fixed deck. New retrieval items are minted every day and must enter a review schedule. Old items must resurface. This is different from a static Anki deck and I need scheduling advice that accounts for it.
- A gamification layer exists (points, a skill/talent tree, streaks, achievements). It is currently incoherent (points earned from studying topic A can only be spent on unrelated topic B), and I need to know whether and how to fix it without corrupting intrinsic motivation.

## What is provably broken today (design the fixes around these)

1. **The retrieval/scheduling loop has never actually run.** In four days and 27 question blocks, at most one answer was ever recorded, because the questions are skippable and the day completes around them. Nothing has resurfaced; difficulty has never calibrated. I need an engine design where the core loop cannot be silently bypassed.
2. **No hint ladder exists.** The question schema has no hint field. After a wrong answer the app says "wrong, one more try" and then pastes the full solution into the field. I know this is the answer-giving anti-pattern; I need the correct alternative specified.
3. **No worked example before the problem, no pretest before the reading.** The generator sometimes asks the learner to compute something it never demonstrated.
4. **No real mastery measurement.** "Rank" is just points spent. There is no model of what I actually know, so the system cannot decide what to teach next or claim I have mastered anything.
5. **Grading integrity is thin.** The LLM grader is a single pass with an optional, error-swallowed verifier. No calibration set, no reliability measurement, no bias correction.
6. **The curriculum has no independent author.** The same daily generation pass that writes today's lesson also implicitly decides what gets taught next, in what order, and whether the content is true. Nothing separate from that one stochastic pass owns sequencing, coverage, or fact-checking. There is no concept graph, no claim ledger, no verifier that is not the same weights that produced the artifact in the first place, and no channel for me to push my own ideas or corrections back into what gets generated tomorrow. Sections H through L design the fix for this specifically: authorship, verification, idea quality, and human steering, not just item generation and grading.

### H. The LLM-core design gap: verification architecture for a model that authors curriculum
This section exists because the failure mode named in point 6 above is not the same failure mode as a bad grade. A mis-grade costs me one data point in the mastery ledger; a false belief installed by a hallucinated "reading" section and never independently checked costs me a wrong mental model that I carry into an interview, with nothing in the current design that would ever surface the error. These need different fixes, and this section specifies the second one.

The single mechanism that makes any of this checkable at all is the generator/verifier asymmetry: verifying a claim is a different, and often easier, computation than generating it, so the same call that produced an artifact must never be the one that blesses it as true (must cite Lightman et al., 2023, arXiv:2305.20050, "Let's Verify Step by Step," for the process-reward-model result this rests on). Every mechanism below is an application of that one idea to a different part of the pipeline.

- **RQ1, curriculum spine.** Specify a versioned concept-graph DAG (nodes are concepts or skills, edges are prerequisite relations, each node carries mastery thresholds and citations to a source I trust) authored through human-approved diffs, not generated fresh each day. The daily LLM call is restricted to surface realization: given a fixed node and its edges, write today's lesson and items for that node; it does not choose which node comes next. Must cite Wenger (1987, Artificial Intelligence and Tutoring Systems) for the domain-model/pedagogical-model split, Brusilovsky (1996, User Modeling and User-Adapted Interaction, "Methods and Techniques of Adaptive Hypermedia") for the concept-network precedent, and Aleven, McLaren, Sewall & Koedinger (2009, International Journal of Artificial Intelligence in Education, on the CTAT example-tracing authoring/runtime split) for the authoring-time versus runtime-generation boundary this recommendation borrows directly. Give the concrete JSON schema for a node and an edge, and the diff format a human approves before it becomes canon.
- **RQ2, claim verification.** Specify a per-lesson claim ledger: every factual assertion in a generated lesson is extracted as a discrete, checkable claim, run through a retrieval-and-entailment check against a trusted source, and assigned to one of three publish bands (auto-publish: high-confidence entailment against a trusted source; human-review: contested or unsourced but plausible; auto-reject: contradicted or unverifiable), with the lesson blocked from publishing any auto-reject claim unless I explicitly override it. Must cite Dhuliawala et al. (2023, arXiv:2309.11495, "Chain-of-Verification Reduces Hallucination in Large Language Models") for the verify-then-revise pattern, Es et al. (2023, arXiv:2309.15217, "RAGAS: Automated Evaluation of Retrieval Augmented Generation") for the faithfulness-scoring mechanism the entailment check can reuse, Wang et al. (2022, arXiv:2203.11171, "Self-Consistency Improves Chain of Thought Reasoning") for a cheap same-model cross-check where no external source exists, and Ji et al. (2023, ACM Computing Surveys, "Survey of Hallucination in Natural Language Generation") for the taxonomy of hallucination types this ledger needs to distinguish (a wrong fact is a different repair than an unsupported inference).
- **RQ3, curriculum drift.** Extend the grader drift protocol in Section D, which only covers grading, to curriculum content itself: pin the exact model, quantization, and prompt-template version used for lesson generation, freeze a golden set of concept-node realizations graded once by me, and re-run that golden set after every model, quantization, or template change, with a numeric threshold that triggers an automatic rollback to the last known-good pinned version rather than a silent continuation on a changed model. Must cite the empirical basis for why this matters even without a deliberate model swap: Chen, Zaharia & Zou's documented finding that a nominally-fixed model's behavior measurably drifts release to release ("How Is ChatGPT's Behavior Changing Over Time?").
- **RQ4, persistent state.** The model is stateless between invocations; what it "knows" about me is only what gets re-injected into the next prompt. Specify a persistent learner-state block (current concept-graph position, recent mistakes, open corrections, standing preferences from the taste ledger in Section J) that is deliberately re-injected on every generation and grading call, with an explicit token-budget and eviction policy for what gets dropped first when the block grows too large for the context window. Must cite Packer et al. (2023, arXiv:2310.08560, "MemGPT: Towards LLMs as Operating Systems") for the paging pattern this borrows: treat the model's context window as working memory and the persistent-state store as the disk it pages in and out of.
- Antipattern to name and reject explicitly: "add RAG, add a verifier pass, add a human-in-the-loop step" is not an answer on its own, and a report that stops there has not actually engaged this section. State precisely why that bundle fails without the specifics above: a verifier built from the same model family as the generator is correlated, not independent, and will share the generator's blind spots; "add RAG" presumes a ground-truth corpus exists for the exact claim being made, which is not true for synthesized or opinionated technical explanations; a human-in-the-loop step with no claim-ledger structure to review against degenerates into rubber-stamping; and none of the three specifies what happens to already-taught, already-tested content when a later pass discovers it was wrong, which is exactly what RQ3's rollback and RQ2's ledger exist to solve.
- Decision table required: node-authorship (human-diff vs LLM-generated) x claim-verification band (auto-publish vs human-review vs auto-reject) x drift-response (rollback vs flag-only), with build cost in hours and my-case verdict for each cell.
- Tempting-but-do-not-build line: a fully automated concept-graph inference system that mines my own mistake history to propose new nodes and edges without my review is tempting and is not worth building before 2026-09-30; hand-authoring the initial graph for my seven role arms is cheap enough, and an unreviewed auto-expanding graph reintroduces exactly the authorship-without-verification problem this section exists to remove.

### I. Beating LLM-averageness: idea quality, novelty, and creative production
The mechanism that produces bland, converged, "safe" model output is not sampling temperature; it is a population-level effect of RLHF alignment training narrowing the distribution of plausible outputs toward a mode (must cite Kirk et al., 2024, ICLR, "Understanding the Effects of RLHF on LLM Generalisation and Diversity," for the specific mode-seeking mechanism). Raising temperature or writing "be creative" into the system prompt treats a symptom at the wrong level: it perturbs one sample without changing which population of outputs the model draws from. Reject both as the load-bearing fix, and reject an invented, un-validated automatic "novelty score" as a substitute for measurement; state why each is a non-mechanism before proposing the real ones below.

- **RQ1, checkpoint split.** Because this system runs a local model daemon rather than a metered API, generation and grading can deliberately run on different checkpoints or different fine-tunes of the same base model: a higher-entropy or less-aligned checkpoint for generation, a more conservative and consistent one for grading, reusing the generator/grader isolation Section D already mandates for integrity reasons. Specify which open checkpoint families plausibly offer this split today given my hardware, and give the cheap version (two prompt personas on the same checkpoint) versus the gold version (two genuinely different checkpoints) with a verdict on whether the gap is worth the extra local storage and load time before the deadline.
- **RQ2, population search over single-shot generation.** Specify a generate-N, embed, cluster, deduplicate, and select pipeline for daily content: generate multiple candidate lessons or item framings, embed them, cluster to detect near-duplicate "safe" outputs, and select from underrepresented clusters rather than the single first sample. Must cite Si, Yang & Hashimoto (2024, arXiv:2409.04109, "Can LLMs Generate Novel Research Ideas? A Large-Scale Human Study with 100+ NLP Researchers") for the specific finding this design targets: LLM-generated ideas cluster into a narrow, repetitive set unless something explicit forces divergence, and that a population-search step measurably increases judged novelty over single-sample generation. Give the concrete pipeline: N to generate, embedding model, clustering method, and selection rule, sized to run within the daemon's realistic per-lesson latency budget from Section D.
- **RQ3, quality-diversity search.** Evaluate whether a full MAP-Elites-style quality-diversity archive, keyed by behavioral descriptors (for example: abstraction level, analogy domain, rhetorical move), is worth building on top of RQ2's simpler cluster-and-select step. Must cite Lehman & Stanley (2011, Evolutionary Computation, "Abandoning Objectives: Evolution Through the Search for Novelty Alone") for the foundational novelty-search argument and Bradley et al. (2023, arXiv:2310.13032, "Quality-Diversity through AI Feedback") for the direct LLM-plus-QD precedent. Give an explicit verdict: state whether maintaining a QD archive is proportionate to a 6-to-8-hour-a-week solo budget, or whether it is a research-grade mechanism that only pays off at a content volume and time horizon this project does not have before 2026-09-30.
- **RQ4, style versus topic.** Specify how exemplars in a style or voice corpus should be tagged: by rhetorical move (analogy-first, counterexample-first, build-from-failure-mode, historical-motivation) rather than by topic, and require the generator to declare which move it is attempting and justify the choice before drafting. Explain why topic-tagging alone produces topical pastiche rather than genuine style transfer, and give the concrete tag taxonomy to start with.
- **RQ5, measuring novelty.** Specify a two-axis human-rating instrument, expert-plausibility (would a senior practitioner find this framing sound) crossed with already-knew-it (is this substantively new to me or a restatement), scored by me on a fixed short scale after each lesson. Must cite Amabile (1982, Journal of Personality and Social Psychology, "Social Psychology of Creativity: A Consensual Assessment Technique") for the CAT methodology this adapts, and Chakrabarty et al. (2024, CHI 2024, "Art or Artifice? Large Language Models and the False Promise of Creativity") for the direct finding that automatic novelty and creativity metrics do not track human judgment, which is why this instrument must be a short human rating, not a formula. Give the exact rating prompt and scale.
- **RQ6, the taste corpus as one artifact with three jobs.** The exemplar bank used to steer generation, the override channel described in Section J, and the novelty benchmark in RQ5 above should be backed by the same underlying corpus, not three separate stores. Specify the schema once here and reference it from Section J rather than duplicating it. Address explicitly: self-refine (single model critiques and revises its own draft) versus multi-agent debate (two model instances argue a position before a final draft) as the mechanism for using this corpus at generation time, with a verdict on which is worth the extra latency; and the crossover point, in terms of taste-ledger entry count, at which retrieval-augmented in-context exemplars stop being sufficient and a small LoRA fine-tune on my own accepted-and-edited content becomes justified.
- Decision table required: averageness countermeasure (checkpoint-split, generate-N-cluster-select, QD archive, style-tagged exemplars) x mechanism-targeted (sampling diversity vs population diversity vs behavioral coverage vs rhetorical variety) x build cost x my-case verdict.
- Tempting-but-do-not-build line: a full quality-diversity archive (RQ3) and a fine-tuned LoRA persona trained on a taste ledger that does not yet have enough entries are both tempting and both premature before 2026-09-30; the generate-N-cluster-select pipeline plus checkpoint split captures most of the measured novelty gain at a fraction of the build cost, and a LoRA trained on fewer than a few hundred taste-ledger entries risks overfitting to noise rather than learning real preference.

### J. Human override: mixed-initiative steering and idea provenance
The current design treats "human in the loop" as an optional input the model may or may not receive. That framing is too weak. Specify instead an architectural gate: no day of curriculum generation runs ungrounded. Every generation call requires either a human-supplied spark (a live confusion, a real source I read, a half-formed idea I want developed) or, absent a fresh spark, the prior day's edit-diff pulled from the taste ledger as its anchor. The reason a diff is the right unit of signal rather than a rating is that an edited output is a gradient (it says what was wrong and in which direction to move) while a scalar thumbs-up or five-star rating is not (must cite Amershi et al., 2014, AI Magazine, "Power to the People: The Role of Humans in Interactive Machine Learning," for the rich-versus-impoverished interactive-machine-learning-signal distinction this rests on). A single user with only weeks of data cannot afford to discard the richer signal by defaulting to ratings.

- **RQ1, initiative state machine.** Must cite Horvitz (1999, CHI, "Principles of Mixed-Initiative User Interfaces") and translate his general principles into a concrete "who initiates today's content" decision table or state machine for this specific system: states include human-supplied spark present, prior-day edit-diff present but no fresh spark, neither present (name the explicit fallback, do not leave this state undefined), and human-requested full override (I write today's brief myself and the model only realizes it). Specify the transition rule between states and what UI affordance on the phone or PWA triggers each one.
- **RQ2, the spark object.** Give the concrete schema: raw text, source type (a thought, a link, a quote, a job description line, a real bug I hit today), freshness timestamp, LLM-extracted candidate concepts this spark maps to in the concept graph from Section H, the pipeline insertion point (does it replace today's planned node, get queued as a future node, or annotate the planned node's realization), a stale-vs-fresh rule for how many days an unused spark stays eligible before it is deprioritized, and the explicit spark-less-day fallback state named in RQ1. This section must reject vague "human in the loop" language and specify this schema concretely, per the tools-for-thought framing of Engelbart (1962, "Augmenting Human Intellect: A Conceptual Framework"), Bret Victor's writing on tools for thought, and Andy Matuschak and Michael Nielsen's "How Can We Develop Transformative Tools for Thought," all of which insist that the human's raw, half-formed idea needs a first-class data structure and a named insertion point in the pipeline, not an ambient "chat with the assistant" surface.
- **RQ3, the taste ledger.** Give the concrete schema for the diff-based store introduced in Section I RQ6: original generated text, my edited version, a structured diff (additions, deletions, substitutions), the concept-graph node it belongs to, and a decision on retrieval-time use (retrieved as an in-context exemplar for future generation of the same or a related node) versus training-time use (folded into a periodic fine-tune once enough entries accumulate). Must cite Amershi, Kulesza et al.'s work on interactive machine learning signal quality (see RQ above) and Madaan et al. on self-refine-style iterative revision for the mechanism by which an edit-diff can be re-fed to the model as a correction signal on the next generation of a similar item. Specify the concrete crossover point, in entry count, at which retrieval stops being sufficient (already asked in Section I RQ6; answer once and cross-reference).
- **RQ4, the affordance set.** Specify the exact set of actions I can take on any generated artifact, accept, reject, rewrite, deepen (ask for more on this specific point before moving on), and a propagation table stating what each action does downstream: does an accept silently confirm the current concept-graph node's realization was good (feeds RQ5 in Section I), does a reject block that node's next realization from reusing the same rhetorical move (feeds Section I RQ4), does a rewrite always produce a taste-ledger entry (RQ3), and does a deepen insert a same-day follow-up or queue a next-day node? State explicitly whether propagation happens same-day (the very next generation call sees the correction) or is batched to the next day, and give a default. Must cite Yannakakis & Liapis's Sentient Sketchbook as the concrete precedent for a co-creative tool where a small, explicit action set on human-authored or human-edited content steers a generative system's subsequent output, rather than a free-text feedback box.
- Decision table required: initiative state (spark present, diff-only, neither, full override) x pipeline behavior (which generation path fires) x build cost x my-case verdict.
- Tempting-but-do-not-build line: a full recommendation system that proactively surfaces sparks from my browsing history or calendar without me explicitly capturing them is tempting and not worth building before 2026-09-30; a one-tap "save as spark" affordance from wherever I already am (notes app, browser) is the cheap version that captures most of the value without the privacy and engineering cost of ambient capture.

### K. The learner as thinker: generative production over passive consumption
Every mechanism above makes the machine's output smarter. None of them, by itself, makes ME a sharper thinker; that requires the design to deliberately withhold the finished thought and force me to produce it. This section specifies that withholding.

- **RQ1, self-explanation over restatement.** Specify a self-explanation prompt scaffold that can distinguish a learner's restatement of the model's own words from a genuinely new causal inference the learner produced. Must cite Chi, de Leeuw, Chiu & LaVancher (1994, Cognitive Science, "Eliciting Self-Explanations Improves Understanding"), Bisra et al. (2018, Educational Psychology Review, "Inducing Self-Explanation: A Meta-Analysis") for the effect size and moderators, and Dunlosky et al. (2013, Psychological Science in the Public Interest, "Improving Students' Learning With Effective Learning Techniques") for where self-explanation ranks against other techniques on cost and utility. Give the concrete grading distinction: what textual or structural signal separates a paraphrase from a new inference, and how the grader in Section D should score each differently.
- **RQ2, forced analogy pairs and the personal idea graph.** Specify a mechanism where, after a concept is first taught, the learner (not the model) is prompted to produce it in their own words, and that self-authored restatement, not the model's original text, is what populates a permanent personal idea graph. Analogies are always presented and required in comparable pairs, never singly, so the learner must actively map structure across two cases rather than passively accept one framing. Must cite Gick & Holyoak (1983, Cognitive Psychology, "Schema Induction and Analogical Transfer") and Gentner (1983, Cognitive Science, "Structure-Mapping: A Theoretical Framework for Analogy") for why a single analogy invites surface-feature pattern-matching while a pair forces structural abstraction.
- **RQ3, what the mastery ledger is actually failing to measure.** Section C's mastery ledger, however well-built, measures retrieval and application within the same kind of problem it was trained on; it does not measure whether I can use a concept to solve a structurally novel problem I have not seen, which is the actual demand of both a live interview and real engineering work. Must cite Bransford & Schwartz (1999, Review of Research in Education, "Rethinking Transfer: A Simple Proposal with Multiple Implications") for the Preparation-for-Future-Learning (PFL) alternative to a static transfer test, Barnett & Ceci (2002, Psychological Bulletin, "When and Where Do We Apply What We Learn? A Taxonomy for Far Transfer") for how far the far-transfer literature says this generalizes, and Perkins & Salomon (1992, "Transfer of Learning") for the low-road/high-road transfer distinction. Specify a concrete PFL-style probe format that can run alongside, not instead of, the mastery ledger.
- **RQ4, the rewrite-gate.** Specify a mandatory gate before any model-authored explanation or analogy becomes a permanent artifact in the personal idea graph: it must first be rewritten by the learner in their own words, and only the rewrite, not the original, is stored as canon. Must cite Kosmyna et al. (2025, MIT Media Lab, "Your Brain on ChatGPT: Accumulation of Cognitive Debt when Using an AI Assistant for Essay Writing Task") for the measured EEG-based cognitive-debt finding this gate is a direct countermeasure to: passively accepting AI-authored content measurably reduces the neural engagement associated with the learner's own idea-generation, and that debt persists even after the assistance is later removed. Specify pre-generation constraint dials (for example, withhold the model's full explanation until after my first attempt is submitted) as the complementary mechanism, and state which of the two, the rewrite-gate or the constraint dial, is cheaper to build and should ship first.
- Decision table required: production-forcing mechanism (self-explanation prompt, analogy pairs, PFL probe, rewrite-gate, constraint dial) x what it protects against (restatement-without-inference, single-framing acceptance, narrow-transfer overclaim, passive-consumption cognitive debt) x build cost x my-case verdict.
- Tempting-but-do-not-build line: an automated linguistic-similarity classifier that scores whether my rewrite is "different enough" from the model's original text is tempting and not worth building before 2026-09-30; a simple length-and-latency heuristic (a rewrite submitted in under N seconds or under M percent of the original's length is flagged for a manual glance) captures most of the gaming-detection value at a fraction of the cost, and Chakrabarty et al.'s finding above already warns that an automatic similarity score is a weak proxy for the actual judgment needed.

### L. Premise critique: is an LLM-authored daily curriculum the right architecture at all, and the master trust table
Every section above assumes the LLM-core architecture is worth hardening rather than replacing. Do not assume that. Steelman three named alternatives and give one explicit verdict, not "a mix, use your judgment": (1) LLM-spine, the current design, where the model generates the day's content and a verification layer (Section H) checks it; (2) human-spine-with-LLM-edges, where I hand-author or hand-select the concept graph and its core explanations up front (a curated syllabus), and the LLM is used only for the edges, quiz-item variation, hints, grading, drilling, never for choosing what gets taught; (3) curated-from-existing-courses, where the curriculum is assembled from existing high-quality material (official docs, a known course, a textbook) with the LLM used only to convert that material into retrieval items and to tutor around it, contributing no original explanatory prose at all.

- **RQ1, debunk the folklore this whole project implicitly assumes.** "A good enough tutor gets you Bloom's two-sigma" is not what the evidence says. Must cite VanLehn (2011, Journal of the Learning Sciences, already cited in Section B) for the actual finding: human tutors average roughly 0.79 SD over classroom instruction and intelligent tutoring systems average roughly 0.76 SD, near parity, nowhere near Bloom's original two-sigma (2.0 SD) claim. Must also cite Kulik & Fletcher (2016, Review of Educational Research, "Effectiveness of Intelligent Tutoring Systems: A Meta-Analytic Review") for a second independent meta-analytic confirmation, Kestin et al. (2024, Scientific Reports, on an AI-tutor RCT that outperformed active-learning classroom instruction) as the strongest pro-LLM-tutoring evidence available, and Bastani et al. (2024, Wharton, "Generative AI Can Harm Learning") as the direct counter-finding that an unguarded GPT tutor measurably harmed learning outcomes relative to no AI access at all, specifically when students used it to get answers rather than explanations. Reconcile these three findings explicitly rather than citing them as a pile of "mixed evidence": what design feature separated the Kestin result from the Bastani result, and does this system's design currently have that feature. Also revisit Khan Academy's Khanmigo split from Section F here: state plainly whether it corroborates architecture (2) above.
- **RQ2, the master decision table.** This is the deliverable this whole report has been building toward. Produce one exhaustive, function-by-function ownership table across every named pipeline function in this report: lesson prose generation, quiz/fill-in item text generation, answer-key authoring, hint-ladder content, curriculum sequencing (which concept-graph node comes next), free-text grading, mastery-ledger updates, gamification/progression updates, tool-and-fact-specific claims (API behavior, pricing, syntax), spark and taste-ledger interpretation (Section J), and novelty/idea generation (Section I), at minimum. For each function, classify it as LLM-owned (no constructible ground truth exists; the model's output stands, with human review as the only backstop), LLM-assisted (the model drafts, a separate mechanism verifies before anything is treated as canon), human-verified (a human must explicitly approve before the artifact is used), or deterministic (no LLM call at all; plain code). For every row classified as LLM-assisted or human-verified, name the specific independent, non-correlated verifier from the relevant section above (H's claim ledger, D's calibration set, B's blind-solvability check); a row that names "a verifier" without naming which one from this report is incomplete.
- **RQ3, the hidden cost trade-off.** Verification has an ongoing per-day cost (my time reviewing claim-ledger flags, taste-ledger diffs, and spark-gated generations); curation has a one-time upfront cost (hand-authoring the concept graph and its core explanations). Give an explicit numeric estimate, in minutes per day, of the ongoing verification-minutes cost implied by the mechanisms in Sections H through K, and an explicit numeric estimate, in hours, of the one-time curation cost of hand-authoring the concept graph for my seven role arms. Compute an explicit break-even week: the point in the roughly nine weeks before 2026-09-30 at which cumulative verification-minutes cost would exceed the one-time curation cost, net against the stated 6-to-8-hour-a-week budget, and state which architecture wins under that arithmetic.
- **RQ4, temperature is not the lever, and neither is more self-generated data.** Reinforce and extend Section I's finding with two citations new to this report: Peeperkorn et al. (2024, ICCC, "Is Temperature the Creativity Parameter of Large Language Models?") for the direct empirical test showing temperature does not reliably track judged creativity, and Shumailov et al. (2024, Nature, "AI Models Collapse When Trained on Recursively Generated Data") for the risk on the other side: if this system's own generated-and-accepted content is later used to fine-tune or steer itself (the LoRA path floated in Section I RQ6), state explicitly what guard prevents a recursive-training collapse where the model increasingly reflects its own prior outputs rather than external ground truth.
- **RQ5, syllabus-as-code as the deterministic gate.** Specify a concrete JSON or YAML schema for a syllabus-as-code artifact (learning objectives, prerequisite edges, assessment criteria, all authored or approved by me before any generation call fires) as the deterministic pre-generation gate that architecture (2) above requires. Must cite Wiggins & McTighe (2005, Understanding by Design) for the backward-design principle this schema operationalizes: define the assessment and the objective before generating the instructional content, not after.
- **RQ6, the verdict.** Give one named verdict among the three steelmanned architectures, or an explicit named hybrid if the evidence genuinely supports one (for example: architecture (2) for the concept-graph spine and core explanations, with architecture (1)'s verification machinery from Section H applied only to the LLM-owned edges). Do not answer with generic "use a mix, apply judgment"; if a hybrid is the honest answer, name exactly which functions from RQ2's table sit on which side of it. State the explicit cost of inaction: what specifically breaks, and by when, if I ship none of Sections H through L and keep the current all-LLM-authored design as is.
- Tempting-but-do-not-build line: a fully human-authored concept graph with zero LLM involvement in sequencing, covering all seven role arms in exhaustive depth before any daily generation begins, is tempting and not worth building before 2026-09-30 as a single upfront project; the break-even analysis in RQ3 should instead recommend a minimal viable graph (core nodes only, expanded incrementally) so curation cost does not itself blow the budget the entire report is constrained by.
